# 架构优化 · 第1步 · 评估提案（体检 + 提案，只提不改）

**做什么**：读工作流的机器可读全景，按架构标尺体检整条写书工作流，找出结构级问题，产出《架构评估报告 + 改造提案》。
**输入**：`ENGINE/tools/graph.json`（★主）+ `ENGINE/工作流总览.md`（权威流程）+ 按需抽读个别节点 md。
**产出**：《架构评估 + 改造提案》。**只提案，不执行**（铁律1：先提案后执行）。
**落盘**：`ENGINE/_架构优化留档/<日期>-<主题>/评估提案.md`，带溯源头。

> 先读《架构优化-总纲》五条铁律。本步只输出判断与建议，**一个节点都不许真动**。

---

## 一、先建全局（从 graph.json）

读 `graph.json`：`nodes`（每个节点的 `简介/工坊/服务/layer`）+ `edges`（`pipeline` 管线 / `reads` 参考）+ `issues`（工具已算出的孤儿/断链/循环）。一遍下来就该能回答"这工作流由哪些工坊、哪些节点、怎么串起来的"。**别整库通读散文档**——只在某个节点的职责需要判定时才抽读它的 md。

## 二、六条架构标尺（逐条体检）

1. **单一职责 / 粒度**：每个节点是不是只干一件事？有没有**胖节点**（一个节点塞了多个本该独立的职责，该拆）？有没有**碎节点**（拆得过细、频繁成对出现、该合）？
2. **管线顺序与缺口**：`pipeline` 顺序合不合理？有没有**该有而缺的步骤**——某产物没人校验、两步之间缺一层必要的转换/收敛、某个门禁缺失？
3. **依赖健康**：`reads` 耦合是否过重（一个节点读一大堆）或过散？有没有**隐藏依赖**（实际要用却没在 frontmatter 声明）、**绕依赖**、**孤儿**（没人引用且不引用别人）、**循环**？
4. **分层与命名一致**：`layer / 工坊 / 服务` 归类对不对？命名是否自洽、有没有**旧代号/历史残留**、同一概念多个叫法？
5. **冗余 / 重复**：有没有两个节点在做同一件事？有没有同一条规则/说明**重复散落**在多处、该收敛到一处再被 reads？
6. **与权威流程一致**：`graph.json` 的实际结构与 `工作流总览.md` 的描述是否一致？不一致处，判断是**文档漂移**（改文档即可）还是**结构漂移**（要动结构）。

## 三、输出格式

**《架构评估报告》**：按上面六维，逐维给"现状 + 发现的问题"（没问题的维度也写一句"健康"）。

**《改造提案》**：每条一个结构问题，字段——
- **问题**：一句话说清结构毛病。
- **建议动作**：增 / 拆 / 合 / 删 / 重接依赖 / 调序（可组合），具体到哪些节点、怎么接。
- **为何现有承载不了 / 职责去哪**：按铁律3 论证必要性（新增→现有为何承载不了；删除合并→职责由谁接管、有无下游依赖）。
- **影响面**：会牵动哪些文件/依赖/《工作流总览》的哪段。
- **风险**：可能引入的断链/循环/语义丢失。
- **优先级**：高/中/低。

> 提案是给作者逐条勾选的清单。**不要在本步替作者拍板，更不要动手改**。

## 四、边界

- 只看**结构/流程**层。碰到"某节点文字/文风该改"→ 记一句"转用词优化分支",不在本步处理。
- 不碰 `BOOKS/` 产物。

## 使用方式

- 全程带跑：「跑架构优化-评估提案」/「从架构角度审一遍工作流、先别改」。
- 高消耗变体（并发子 agent 分维度体检）：跑前先报规模、经作者同意（见总纲规模提示）。
