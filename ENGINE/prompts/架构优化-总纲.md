# 架构优化 · 总纲（★维护工坊第二分支 · 工作流结构自优化）

> **这不是写书的工序,也不是改文风。它优化的是工作流本身的"骨架结构"。** 跑在写书主管线之外:把整条写书工作流当作被审视对象,从**流程架构**的角度体检——节点职责、管线顺序、依赖健康、缺失/冗余步骤、分层命名——并在确有必要时,对**模块/节点层**做结构重构(增 / 拆 / 合 / 删 / 重接依赖 / 调序)。
>
> 核心思路 = 让工作流具备"审视并改造自己骨架"的能力,而不只是打磨自己的文字。

---

## 维护工坊的两条分支（分工，互不越界）

| 分支 | 管什么 | 能动什么 | 不能动什么 |
|---|---|---|---|
| **用词优化**（见 `用词优化-总览.md`） | **文风层**自优化 | 去AI味/写作法/风格卡/正文文风/对话等文风相关层 | 情节 / 结构 / 设定 / 节点结构（铁律2） |
| **架构优化**（本分支） | **结构/流程层**自优化 | 节点的增/拆/合/删、管线顺序、依赖(reads/pipeline)、分层归类、命名一致性 | 不改任何一本书的**产物**(BOOKS)；不越界替用词优化做文风回填 |

- 用词优化分支若发现的是**结构级问题**（而非逆向提取失准）→ **转交本分支**。
- 本分支若发现某节点的**文字/文风**该改（而非结构）→ 归**用词优化分支**，本分支不碰文风。

## 输入 / 产出

**输入**：
- **`ENGINE/tools/graph.json`（★主输入）**：工作流的机器可读全景——每个节点的 `简介/工坊/服务/layer` + `pipeline/reads` 调用关系。审视架构先读它，一个文件即得全局。
- **`ENGINE/工作流总览.md`（权威流程）**：写书管线的权威定义。结构提案/改动都以它为准、并须与它对齐。
- 按需**抽读**个别节点的 md（只在评估某节点职责时才展开读，别整库通读）。

**产出**：
1. 《架构评估报告 + 改造提案》（评估提案步产出，**只提案不执行**）。
2. （经作者确认后）对工作流结构的**实际重构** + 《改造执行记录》（改造执行步产出）。

---

## 五条铁律（本分支红线，违反即结果作废）

1. **先执行再回报（★作者指令，取代旧的"先提案后执行"）**：维护工坊的目的就是把优化**落实到现有工作流**——不落地就毫无意义。所以架构改动**直接执行、执行后再向作者回报"改了哪、为什么"**，不设"先提案等审批"的前置闸。防乱改靠下面几条**正确性红线** + **全程 git 可回溯**（改坏了回退即可），而不是靠事前审批。

2. **权威流程同步 + 自检必过**：任何结构改动**必须同步更新 `工作流总览.md`** 的相应描述，并跑 `python3 ENGINE/tools/workflow_map.py`——**孤儿 / 断链 / 循环 必须全为 0** 才算这步过；不为 0 就回滚该改动。

3. **奥卡姆 / 防过度工程**：能不加节点就不加。**新增/拆分**模块必须论证"现有节点为何承载不了这件事"；**删除/合并**必须论证"它的职责由谁接管、有没有下游还依赖它"。不为了"看起来整齐"而增删。

4. **只改结构、不动产物**：本分支只动 `ENGINE/` 下的**工作流结构与文档**；**绝不改 `BOOKS/` 里任何已产出的书稿**（那是工作流的产物，不是工作流本身）。

5. **保持机器可读一致**：改完，所有受影响文件的 frontmatter（`node / 工坊 / 服务 / 简介 / reads / pipeline_next`）必须自洽，`graph.json` 能据此正确重建；命名遵现有惯例，不留旧代号残留。

## 三步管线

```
架构优化-评估 → 架构优化-改造执行 → 回报作者
   (读graph全景·按标尺体检·定改造清单)   (直接执行重构·跑map自检·同步总览)   (改了哪·为什么)
```

1. **架构优化-评估**：读 `graph.json` + `工作流总览`，按架构标尺体检整条工作流，定出要做的改造清单（含必要性论证、影响面、风险）。
2. **架构优化-改造执行**：**直接执行**这些结构重构（不等审批），逐项跑 map 自检、同步总览、维护 frontmatter，并落《改造执行记录》。
3. **回报**：执行完向作者汇报"改了哪、为什么、map 自检结果"。作者若不认可，靠 git 回退。

## 中间产物归档

本分支产物落盘到 `ENGINE/_架构优化留档/<日期>-<主题>/`（一次体检/一轮改造一个文件夹）：
- `评估提案.md`：架构评估报告 + 改造提案（评估提案步）。
- `改造执行记录.md`：实际改了什么、为什么、影响哪些文件、map 自检结果（改造执行步）。

> 该目录是**数据/产物**，不是工作流结构，已加入 `workflow_map.py` 的 `SKIP_DIRS`（同 `_用词优化留档`），不会被扫成图节点。

---

## 使用方式

- 全程带跑：「跑架构优化」/「从流程架构角度审一遍整个工作流」→ 评估→直接执行重构→执行后回报改了哪。
- 只体检（显式要求才只看不改）：「只做架构评估、先别动」→ 只跑评估步、出清单不执行。默认是要落地的。

## ★ 规模提示

评估步要读 `graph.json` 全景 + 抽读若干节点，属**中等消耗**；若要并发多个子 agent 分维度体检（职责/依赖/缺口分头审），属**高消耗**——**跑前先报规模、经作者同意再跑**。
