# 架构优化 · 第2步 · 改造执行（只执行确认项）

**做什么**：作者从上一步《改造提案》里**逐条勾定**要执行的条目后，本步把这些结构改动**实际做出来**，并逐项自检、同步权威流程、维护机器可读一致性。
**输入**：上一步 `评估提案.md` + **作者已确认要执行的条目清单**。
**产出**：对工作流结构的实际重构 + `改造执行记录.md`。
**落盘**：记录写入 `ENGINE/_架构优化留档/<日期>-<主题>/改造执行记录.md`。结构改动本身改的是各节点 md / 目录 / frontmatter。

> ★ 总纲铁律1（先执行再回报）在这一步落地：**直接执行评估步定的清单，不等作者审批**；执行完向作者回报改了哪、为什么。防乱改靠下面的正确性红线 + git 可回溯。

---

## 一、开工前置（correctness，不是审批）

- 手上有评估步定的**改造清单**（做哪几条、为什么）。没有清单就先跑评估步、别凭空乱改。
- 每条改动开工前，对照铁律3（奥卡姆/必要性）再自检一次：这条确实值得做、且现有节点承载不了。
- 不夹带清单外的即兴改动（要改先补进清单并说明理由）。

## 二、执行动作类型（模块层重构）

- **增节点**：新建 md（写全 frontmatter：node/layer/role/工坊/服务/简介 + reads/pipeline_next），把它接进管线（上下游的 pipeline_next / 相关节点的 reads）。
- **拆节点**：一个胖节点拆成多个、按职责分家，重接各自的依赖，原节点或改造或退役。
- **合并**：多个碎节点并成一个，迁移它们的 reads/被引用关系到合并后的节点。
- **删除**：确认**无下游还依赖**后删除，并清理所有指向它的 reads/pipeline_next（否则会断链）。
- **重接依赖**：调整 reads / pipeline_next。
- **调序**：改 pipeline 顺序。

## 三、每条改动的收尾自检（★硬规则，逐条做，不通过就回滚该条）

1. **跑依赖图自检**：`python3 ENGINE/tools/workflow_map.py`——**孤儿 / 断链 / 循环 必须全为 0**。不为 0，说明这条改动引入了结构病 → **回滚该条**，重想。
2. **同步权威流程**：结构变了，**必须同步更新 `ENGINE/工作流总览.md`** 相应描述（管线顺序、节点职责、加载策略等），让权威流程文档与真实结构一致。
3. **维护 frontmatter**：所有受影响文件的 `node/工坊/服务/简介/reads/pipeline_next` 自洽、命名遵惯例、无旧代号残留。
4. **记录**：在 `改造执行记录.md` 里写清——做了哪条提案、动了哪些文件、为什么、map 自检结果（issues 是否全 0）。

> 本步天然覆盖项目硬规则「改过工作流 md → 跑 workflow_map.py」——这里把它作为每条改动的收尾闸强制执行。

## 四、边界

- 只执行**被确认的结构改动**；文风/文字改动归用词优化分支，不在此处夹带。
- 不碰 `BOOKS/` 产物。

## 使用方式

- 全程带跑：「这几条提案照做：<编号>」→ 本步逐条执行 + 自检 + 同步总览 + 落记录。
